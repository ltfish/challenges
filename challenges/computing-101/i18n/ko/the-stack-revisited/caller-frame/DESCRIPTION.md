스택은 임시 데이터와 반환 주소를 담는 것 말고도 함수의 _지역 변수_ 를 담습니다. 프로그램의 다른 함수가 꼭 필요로 하지는 않는, 그 함수만의 데이터죠.
해커가 프로세스 안에서 "코드 실행"을 얻은 보안 상황에서 이 변수들은 활짝 펼쳐진 책이나 다름없습니다. 프로세스 안의 코드가 스택 여기저기에서 데이터를 읽는 것을 막는 것은 아무것도 없으니까요!

이 챌린지는 그 개념을 살펴봅니다.
다시 한 번 챌린지가 호출할 `solve` 함수를 작성하는데, **챌린지는 인자를 하나도 넘기지 않습니다**.
대신 챌린지의 `caller` 함수가 여러분을 호출하기 전에 자기 지역 변수에 플래그를 저장해 둡니다.
여러분은 호출자의 "프레임"(함수의 지역 변수와 돌아갈 반환 주소를 포함하는 스택의 한 부분)으로 손을 뻗어 그 바이트를 가져와야 합니다.

**잠깐, 뭐라고요?**  
왜 이것이 가능한지 짚어봅시다.
이 챌린지에서 `main` 함수가 `caller` 함수를 호출하고, 그것이 다시 여러분의 `solve` 함수를 호출합니다.
챌린지의 `caller` 함수가 `call solve`를 실행하기 직전에 스택은 이랬습니다:

```text
                                          [smaller addresses]
   +───────────────────────────────────+  ◀── rsp, immediately before `call solve`
   │ caller's local region             │
   │ ... your flag is in here ...      │
   +───────────────────────────────────+
   │ caller's saved rbp                │
   +───────────────────────────────────+
   │ return address (back to main)     │
   +───────────────────────────────────+
   │ ... main's frame ...              │
   +───────────────────────────────────+
                                          [larger addresses]
```

`call solve` 명령어는 두 가지 일을 합니다:

1. 반환 주소를 스택에 push합니다(8바이트). **push는 `rsp`를 감소시키므로**, 반환 주소는 이미 스택에 있던 것보다 _작은_ 주소에 놓입니다.
2. 여러분의 코드로 점프합니다.

그 첫 단계가 중요합니다. 스택은 여러분이 예상할 법한 방향과 반대로 자랍니다.
`pop`은 사실 `rsp`에 8을 더하고, `push`는 8을 뺍니다.
직관에 어긋나는 개념이라 학습자들이 자주 헷갈립니다.
스택을 8바이트 폭의 종이라고 생각하면, 그 종이의 맨 아래부터 쓰기 시작해서 `push`할 때마다 한 줄씩 위로 올라가는 셈입니다.
다시 말해 `pop rdi`는 `mov rdi, [rsp]; add rsp, 8`과 같고, `push rdi`는 `sub rsp, 8; mov [rsp], rdi`와 같습니다.

그래서 스택 이야기를 혼란 없이 하기란 거의 불가능합니다.
예를 들어 수학 배경이 있는 사람은 좌표 0을 종이의 아래나 왼쪽으로 생각하는 경향이 있고, 비디오 게임이나 웹 개발 배경이 있는 사람은 0을 위나 왼쪽으로 생각하는 경향이 있습니다.
그래서 "높은 주소", "낮은 주소" 같은 말의 정의를 두고 큰 혼란이 생깁니다.
사람마다 이것을 다루는 방식이 다릅니다.
이 문서에서는 가로 공간이 부족해서 0(위)부터 0xffffffff(아래)로 그림을 그리지만, 가로 공간에 제약이 없는 일상에서는 메모리를 "왼쪽"(0)에서 "오른쪽"(0xffffffff)으로 생각합니다.

아무튼 여러분의 `solve`가 실행되기 시작하는 순간 스택은 이렇습니다:

```text
                                          [smaller addresses, where rsp goes if you grow your own frame]
   +───────────────────────────────────+
   │ return address (back to caller)   │  ◀── rsp points here
   +───────────────────────────────────+
   │ caller's stack frame              │
   │ ... your flag is in here ...      │
   +───────────────────────────────────+
   │ return address (back to main)     │
   +───────────────────────────────────+
   │ ... main's frame ...              │
   +───────────────────────────────────+
                                          [larger addresses]
```

호출자의 지역 변수는 여러분의 `rsp`보다 _큰_ 주소, 그림에서는 `rsp` 아래에 있습니다. 원하는 데이터는 그 영역 어딘가에 있습니다.
그것을 찾으려면 `rsp`에서 **양수** 오프셋으로 메모리를 인덱싱하면 됩니다.

반대로 가면(음수 오프셋, `rsp`보다 _작은_ 주소, 그림에서 `rsp` 위쪽) 할당되지 않은 스택 공간이 나옵니다.
거기에는 (아직!) 쓸모 있는 것이 없습니다.

여러분의 `solve`가 실행되기 시작할 때 배치는 이렇습니다:

```text
   [rsp + 0x00]   your return address (back into caller's code)
   [rsp + 0x08]   first byte of caller's local region
   ...
   [rsp + 0x40]   the flag (copied here by the caller)
   ...
   [rsp + 0x110]  caller's return address (back to main)
```

여러분이 할 일은 호출자의 프레임으로 손을 뻗어 `[rsp + 0x40]`에 있는 플래그를 가져와 stdout으로 `write`하는 것입니다(`write` 시스템 콜은 이미 알고 있죠!).
제대로 하면 여러분의 `solve`가 플래그를 출력해 줍니다!
