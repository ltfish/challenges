앞 레벨에서는 각 바이트를 스택에 써서 "/flag" 파일 이름을 만들었습니다.
유용한 기법이지만 쓰기 번거롭고 이해하기도 어렵습니다(그런 식으로 쓴 긴 문장에서 오타를 찾는다고 상상해 보세요!).
이 챌린지에서는 더 나은 방법을 보여드립니다.

다행히 어셈블리에는 실행할 목적이 아닌 바이트도 담을 수 있습니다.
예를 들어 마지막 `exit` 시스템 콜 뒤에 그 바이트들을 두면 CPU는 거기에 닿기 전에 멈춥니다.
그 바이트들은 여전히 프로그램 메모리에 남아 있지만, 명령어로 해석되어 프로그램을 죽이지는 않습니다.

문자열을 위해 어셈블러는 이런 바이트를 지정하는 편리한 지시자를 제공합니다:

```asm
_start:
    ...
    mov rax, 60
    syscall           // exit!
path:
    .asciz "/flag"    // never executed, but still there!
```

`.asciz` 지시자는 문자열의 바이트와 함께, 리눅스가 파일 이름 끝에 기대하는 종료용 0 바이트를 함께 내보냅니다.
`path:` 레이블은 그 바이트들이 시작하는 위치를 표시합니다.
뒤쪽 챌린지에서 컴파일된 바이너리가 저장된 문자열의 포인터를 불러오는 것을 보게 될 텐데, 그것이 바로 같은 아이디어를 반대편에서 본 모습입니다. 바이트는 프로그램 안에 저장되어 있고, 명령어가 실행 시점에 그 주소를 계산하는 것이죠.

그러면 문제가 하나 남습니다. 이 경로를 `open` 시스템 콜에 넘기려면 그 주소를 `rdi`에 넣어야 합니다.
옛날에는 프로그램이 항상 메모리의 같은 주소에 적재되었기 때문에 이렇게 하드코딩할 수 있었습니다:

```asm
_start:
    ...
    mov rdi, path    // this would tell the assembler to store the address of `path` in rdi
    ...
path:
    .asciz "/flag"
```

안타깝게도 사이버 보안 맥락에서는 **이것이 동작하지 않습니다**!
현대 소프트웨어는 옐로 벨트에서 다룰 보안상의 이유로, 메모리 어디에나 적재될 수 있도록 컴파일됩니다.
즉 소프트웨어를 어셈블하는 시점에 _어셈블러는 올바른 주소를 모릅니다_.
평범한 애플리케이션에서는 시작 시점에 이를 해결할 수 있지만, 현대 CPU는 다른 방식으로 이 문제를 풀었습니다. 바로 _명령 포인터 상대 주소 지정(Instruction Pointer Relative Addressing)_ 입니다.


64비트 x86에서 _명령 포인터_ (`rip`)는 CPU가 _다음에_ 실행할 명령어의 주소를 항상 담고 있는 레지스터입니다.
다만 `rdi` 같은 것보다 쓰임이 제한적이라는 점에서 평범한 레지스터는 아닙니다(이는 x86의 특이한 점이며, 다른 많은 아키텍처는 명령 포인터에 직접 접근할 수 있게 해 줍니다).
그렇지만 64비트 x86은 메모리 읽기와 쓰기에 `rip` 기준 상대 주소를 쓰는 것은 허용합니다.
예를 들면:

```asm
_start:
    ...
    mov rdi, [rip+path]
    ...
path:
    .asciz "/flag"
```

**이것도 우리가 원하는 것이 아닙니다!**
왜냐고요? 이것은 그 바이트들의 주소를 `rdi`에 넣는 것이 아니라, `[rip+path]`에 있는 8바이트를 `rdi`로 _읽어오기_ 때문입니다.
`rdi`에는 `'f'`, `'l'` 같은 값들이 들어가겠지만, `open` 시스템 콜에 필요한 것은 값이 아니라 주소입니다.

다행히 읽기와 _거의_ 같지만, 읽었을 주소를 `rdi`(또는 다른 레지스터)에 넣어주는 명령어가 있습니다.
그 명령어가 **l**oad **e**ffective **a**ddress입니다(여기서 _effective_ 는 CPU가 필요한 계산, 여기서는 명령 포인터에 오프셋을 더하는 계산을 알아서 해준다는 뜻입니다):

```asm
_start:
    ...
    lea rdi, [rip+path]
    ...
path:
    .asciz "/flag"
```

이렇게 하면 문자열의 내용이 아니라 "/flag" 문자열의 주소가 `rdi`에 들어갑니다.
`path`를 `"/flag\0"`의 첫 바이트가 있는 주소라고 생각하세요. `mov`는 거기서 바이트를 복사하고, `lea`는 주소를 복사해서 커널이 널 바이트가 나올 때까지 그 바이트들을 훑을 수 있게 합니다.

여기서 계산에 대해 짧게 짚고 넘어가면, 위에서는 `[rip+path]`라고 썼지만 실제로 `rip`에 더해지는 것은 (다시 말하지만 `lea` 다음 명령어를 가리키는) `rip`와 "/flag" 문자열 사이의 주소 차이입니다.
묘한 문법이고, x86의 또 하나의 자잘한 특이점입니다.

이 챌린지에서는 이것을 써서 `open`에 넘길 경로를 설정하세요.
여러분의 프로그램은 저장된 파일 이름을 열고, 반환된 fd에서 메모리로 `read`하고, 읽은 만큼만 정확히 `write`하고(read-exact에서처럼 `mov rdx, rax`), 코드 `42`로 `exit`해야 합니다.
새로운 부분은 이것입니다:

1. 코드 뒤에 `.asciz`로 파일 이름을 저장합니다.
2. `lea rdi, [rip + path]`로 `open`에 넘길 파일 이름 주소를 불러옵니다.
