앞 레벨에서는 파일 이름이 프로그램의 인자로 넘어왔습니다.
그런데 경로를 이미 알고 있는 파일을 열어야 한다면 어떨까요?
코드에 문자열을 하드코딩하는 방법은 여러 가지지만, _pwn.college에서 여러분이 작성할 코드의 성격상_ 실제 소프트웨어 개발보다는 소프트웨어 익스플로잇에 어울리는 "해커" 방식을 쓰겠습니다.
파일 이름 문자열을 한 바이트씩 스택에 써서 프로그램에 직접 하드코딩할 것입니다!

`open` 시스템 콜은 파일 이름의 _포인터_ 를 원하므로, `/ f l a g` 바이트가 메모리 어딘가에 저장되어 있어야 합니다.
이미 쓰기 가능한 메모리 주소를 하나 알고 있습니다. 바로 `rsp`(스택)죠.
각 문자를 한 바이트씩 쓸 수 있습니다:

```asm
mov BYTE PTR [rsp], '/'
mov BYTE PTR [rsp+1], 'f'
mov BYTE PTR [rsp+2], 'l'
mov BYTE PTR [rsp+3], 'a'
mov BYTE PTR [rsp+4], 'g'
mov BYTE PTR [rsp+5], 0
```

여기서 몇 가지 짚을 것이 있습니다:

- **`BYTE PTR`**: `[rsp]` 같은 메모리 주소에 _즉시값_ (숫자나 문자)을 쓸 때, CPU는 몇 바이트를 쓰려는 것인지 모릅니다. 하나? 둘? 여덟? `BYTE PTR`는 "정확히 한 바이트를 뜻한다"고 알려주는 _크기 지시자_ 입니다. 이것이 없으면 어셈블러는 무엇을 원하는지 몰라 명령어를 어셈블하지 않습니다.

- **작은따옴표**: 어셈블리에서 `'f'`처럼 작은따옴표로 감싼 문자는 그 문자의 1바이트 ASCII 값을 나타냅니다. 그러니 `'f'`는 `0x66`을 편하게 쓴 것이고, `'/'`는 `0x2f`입니다.

- **널 바이트**: 마지막에 쓰는 바이트 `0`은 특별한 _널_ 바이트입니다. 리눅스는 이것으로 문자열이 어디서 끝나는지 압니다. 여러분이 준 포인터에서 시작해 바이트를 읽다가 `0` 바이트를 만나면 멈추죠. 이것이 없으면 `open`은 `"flag"` 너머 스택에 있는 아무 데이터까지 계속 읽어서, 말도 안 되는 이름의 파일을 열려고 하게 됩니다!

이 바이트들을 쓰고 나면 `rsp`는 널로 끝나는 문자열 `"/flag"`를 가리키게 되어 `open`에 넘길 준비가 됩니다.

**여러분 차례입니다!**
이번에는 프로그램에 인자가 넘어오지 않습니다.
파일 이름을 직접 만들어야 합니다.

여러분의 프로그램은 다음을 해야 합니다:

1. `mov BYTE PTR [rsp+N], ...`로 `"/flag\0"`을 한 바이트씩 스택에 씁니다
2. 그것을 `open`합니다(시스템 콜 `2`): `rdi` = `rsp`(방금 쓴 문자열), `rsi` = `0`
3. 반환된 fd에서 메모리로 `read`합니다(시스템 콜 `0`), 넉넉한 크기로요
4. `read`가 반환한 바이트 수만큼 정확히 stdout에 `write`합니다(시스템 콜 `1`)
5. 코드 `42`로 `exit`합니다(시스템 콜 `60`)
