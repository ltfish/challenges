`|`를 쓰는 파이프를 배웠고, 프로세스 치환이 임시 이름 있는 파이프(`/dev/fd/63` 같은)를 만든다는 것도 보았습니다.
파일 시스템에 계속 남아 있는 _영속적인_ 이름 있는 파이프를 직접 만들 수도 있습니다!
이것을 **FIFO** 라고 부르며, First (byte) In, First (byte) Out의 줄임말입니다.

FIFO는 `mkfifo` 명령어로 만듭니다:

```console
hacker@dojo:~$ mkfifo my_pipe
hacker@dojo:~$ ls -l my_pipe
prw-r--r-- 1 hacker hacker 0 Jan 1 12:00 my_pipe
hacker@dojo:~$ ls -l some_file
-rw-r--r-- 1 hacker hacker 0 Jan 1 12:00 some_file
hacker@dojo:~$
```

권한 맨 앞의 `p`를 보세요. 그것이 파이프라는 표시입니다!
위 예시의 `some_file` 같은 일반 파일 맨 앞에 오는 `-`와는 확연히 다릅니다.

프로세스 치환이 만드는 자동 이름 있는 파이프와 달리:

- FIFO는 어디에 만들지 여러분이 정합니다
- 지울 때까지 계속 남아 있습니다
- 어떤 프로세스든 경로로 쓸 수 있습니다(예: `echo hi > my_pipe`)
- `ls`로 볼 수 있고 파일처럼 살펴볼 수 있습니다

FIFO의 한 가지 문제는, 파이프의 읽는 쪽과 쓰는 쪽이 모두 준비될 때까지 그에 대한 모든 연산이 "블록"된다는 점입니다.
예를 들어 다음을 봅시다:

```console
hacker@dojo:~$ mkfifo myfifo
hacker@dojo:~$ echo pwn > myfifo
```

`echo pwn > myfifo`를 처리하려고 bash는 `myfifo` 파일을 쓰기 모드로 엽니다.
그런데 이 연산은 무언가가 그 파일을 읽기 모드로도 열어(그래서 파이프가 완성되어야) 비로소 진행됩니다.
그것은 다른 콘솔에서 할 수 있습니다:

```console
hacker@dojo:~$ cat myfifo
pwn
hacker@dojo:~$
```

여기서 무슨 일이 일어났을까요?
`cat myfifo`를 실행하자 파이프의 양쪽 연결이 모두 갖춰지면서 _블록이 풀렸고_, 그래서 `echo pwn > myfifo`가 실행되어 `pwn`을 파이프로 보냈고, `cat`이 그것을 읽었습니다.

물론 이런 일은 일반 파일로도 어느 정도 할 수 있습니다. 파일에 `echo`로 써넣고 `cat`으로 읽어내는 법을 배웠으니까요.
그런데 왜 굳이 FIFO를 쓸까요?
주요 차이는 다음과 같습니다:

1. **디스크 저장 없음:** FIFO는 데이터를 메모리에서 프로세스 사이로 곧장 전달합니다. 디스크에 저장되는 것은 없습니다
2. **일회성 데이터:** FIFO에서 한 번 읽은 데이터는 사라집니다(데이터가 남아 있는 파일과 다릅니다)
3. **자동 동기화:** 쓰는 쪽은 읽는 쪽이 준비될 때까지 기다리고, 그 반대도 마찬가지입니다. 이것은 사실 유용합니다! 자동 동기화를 제공하니까요. 위 예시를 생각해 보면, FIFO에서는 `cat myfifo`와 `echo pwn > myfifo` 중 무엇을 먼저 실행하든 상관없습니다. 서로를 기다릴 뿐이니까요. 파일이라면 쓰는 쪽을 읽는 쪽보다 먼저 실행하도록 신경 써야 합니다.
4. **복잡한 데이터 흐름:** FIFO는 복잡한 데이터 흐름을 만들고, 데이터를 유연하게 합치고 나누는 데 유용합니다. 예를 들어 FIFO는 여러 읽는 쪽과 쓰는 쪽을 지원합니다.
